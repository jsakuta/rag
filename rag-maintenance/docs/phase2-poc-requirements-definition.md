## 2. システム概要

### 2.1 背景

当行では、チャットボットシステムをLakeel MessengerからMicrosoft Teams（M365）へ移行するプロジェクトを推進している。現行システムでは、事務改定（通達・規程等の変更）が発生した際、シナリオ・FAQの更新漏れが課題となっている。

**現状の課題:**

- 事務改定の影響範囲を中村氏が手動で監視し、事後的に各チームへ連絡する属人的な運用
- 約70カテゴリ・約3,000件のFAQに対し、複数カテゴリにまたがる影響の把握が困難
- シナリオの修正漏れにより、チャットボットが誤った情報を返すリスク
- FAQ削除の漏れにより、AIが古い情報を学習してしまうリスク

### 2.2 目的

Azure AI Searchのハイブリッド検索（ベクトル検索＋キーワード検索＋Semantic Ranker）を活用し、事務改定の内容から影響を受けるシナリオ・FAQを自動検出する仕組みを構築する。Phase2 PoCでは、Azureクラウド環境上でこの検索基盤が正しく動作することを検証する。

### 2.3 段階設計

本システムは段階的に機能を拡充する。Phase2 PoCではStep 1を対象とする。

| 段階 | トリガー | 概要 | 状態 |
|------|---------|------|------|
| Step 1 | 担当者がTeamsで手入力 | AI検索 → 影響候補表示 → 担当者判断 | ← **Phase2 PoC対象** |
| Step 2 | オート議事録から自動抽出 | 会議での改定決定 → 自動検索 → Teams通知 | 中期目標 |

※ 当初検討していたStep 3（PowerEgg WF連携による二段階承認）は、「改定内容」と「影響範囲」が本質的に同時に検討されるため非現実的と判断し、採用しない。

### 2.4 Phase2 PoCの範囲

**対象範囲:**

| 項目 | 内容 |
|------|------|
| トリガー | 担当者がTeams Bot上で事務改定の内容をテキスト入力 |
| 検索対象 | シナリオ（数百件）＋ FAQ（約3,000件） |
| 検索方式 | ハイブリッド検索（ベクトル＋キーワード）＋ Semantic Ranker |
| 出力 | 影響候補一覧（Adaptive Cardでタブ切り替え表示） |
| ユーザー操作 | 候補確認 → シナリオは修正判断、FAQは削除判断 |
| 追加検証 | 画像ベクトル化（Azure Visionマルチモーダル）の技術検証 |

**対象外範囲:**

| 項目 | 理由 |
|------|------|
| SharePoint PDF自動検知 | Step 2以降の機能（Event Grid連携） |
| PDF差分抽出 | Step 1では手入力のため不要 |
| レビューUI（Teams Tab） | PoCではAdaptive Cardでの候補表示に留める |
| 進捗管理・リマインド | PoCでは対象外 |
| FAQ削除・シナリオ修正の実行 | 本格実装フェーズ |
| カテゴリ別自動振り分け通知 | Step 2以降 |

### 2.6 Phase1からの設計判断

Phase1のローカル検証で以下の知見を得ており、Phase2 PoCの設計に反映する。

| 検証結果 | 設計判断 |
|---------|---------|
| 原文検索とLLMクエリ拡張検索で検索精度に有意な差がなかった | **原文検索に統一**。LLMによるクエリ拡張（Multi-Query Search）は採用しない |
| キーワード完全一致検索（ケース⑤⑥）で100%検知を達成 | キーワード一致モードを独立した検索モードとして実装 |
| AIが人間の見落とし2件を発見 | 意味検索の有効性を確認。Semantic Rankerとの組み合わせで精度向上を期待 |
| 1件未検知（画像内テキスト変更） | Phase2 Week 3で画像ベクトル化の追加検証を実施 |

**Multi-Query Search廃止の影響:**

原文検索に統一することで、以下のリソースが不要となり、構成が大幅に簡素化される。

| 廃止リソース | 理由 |
|-------------|------|
| Azure OpenAI GPT-4o-mini | クエリ拡張に使用予定だったが、原文検索で十分な精度を確認済み |
| Azure Functions (Consumption) | GPT-4o-mini呼び出しとスコア統合のオーケストレーションに使用予定だったが、不要に |

### 4.2 機能詳細

#### FR-001: 改定内容テキスト入力

| 項目 | 内容 |
|------|------|
| 概要 | 担当者がTeams Bot上で事務改定の内容を自然言語テキストとして入力する |
| トリガー | ユーザーがTeams Botにメッセージを送信 |
| 入力 | 自然言語テキスト（改定内容の説明）。最大2,000文字 |
| 出力 | 検索モード選択UIの表示（Adaptive Card） |
| 処理詳細 | 1. Bot（Azure Web App上で稼働）がテキストを受信<br>2. テキスト長の検証（2,000文字以内）<br>3. 検索モード選択Cardを返却 |
| 例外処理 | テキスト長超過時はエラーメッセージを返却 |

**入力例:**

```
口座開設時の本人確認書類が変更になりました。
マイナンバーカードを提示した場合、他の本人確認書類は不要となります。
従来は2点必要でしたが、1点で可となります。
```

#### FR-002: 検索モード選択

| 項目 | 内容 |
|------|------|
| 概要 | 担当者が検索モードを選択する |
| 入力 | Adaptive Cardのボタン選択 |
| 出力 | 選択されたモードで検索実行 |

**選択肢:**

| モード | 用途 | 説明 |
|-------|------|------|
| 意味検索 | 内容変更型の改定 | 入力テキストと意味的に関連するシナリオ・FAQを検索 |
| キーワード一致検索 | 名称変更型の改定 | 指定キーワードを含む全件を漏れなく抽出 |

#### FR-003: 影響候補検索（意味検索モード）

| 項目 | 内容 |
|------|------|
| 概要 | 入力テキスト（原文）でハイブリッド検索を実行し、影響候補を検索する |
| 入力 | 改定内容テキスト（原文をそのまま使用） |
| 出力 | 影響候補リスト（rerankerScore付き） |

**検索方式（原文検索）:**

Phase1の検証で、原文検索とLLMクエリ拡張検索で精度に有意な差がないことを確認済み。構成の簡素化のため、原文テキストをそのまま検索クエリとして使用する。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  原文検索方式                                                                │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  入力テキスト（原文）                                                       │
│  「本人確認書類が2点から1点に変更（マイナンバーカード提示時）」             │
│       │                                                                     │
│       ↓                                                                     │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  Azure AI Search ハイブリッド検索                                    │   │
│  │                                                                     │   │
│  │  ① ビルトインVectorizerが原文テキストを自動ベクトル化               │   │
│  │     → ベクトル検索（cosine類似度）                                  │   │
│  │                                                                     │   │
│  │  ② 同時にキーワード検索（ja.microsoftアナライザー）                 │   │
│  │     → BM25スコアリング                                              │   │
│  │                                                                     │   │
│  │  ③ RRF（Reciprocal Rank Fusion）でスコア統合                       │   │
│  └──────────────────────────────────┬──────────────────────────────────┘   │
│                                     │                                       │
│                                     ↓                                       │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  Semantic Ranker で最終スコアリング                                  │   │
│  │  ・rerankerScore ≥ 1.5 のデータを候補として採用                    │   │
│  │  ・上位N件を返却（デフォルト: 20件）                                │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**構成上のポイント:**

- Botアプリ（Azure Web App）から Azure AI Search REST API を直接呼び出す
- LLMによるクエリ拡張を行わないため、Azure FunctionsやGPT-4o-miniは不要
- クエリ時のベクトル化はAI Searchのビルトインvectorizer（text-embedding-3-large）が自動処理

#### FR-004: 影響候補検索（キーワード一致モード）

| 項目 | 内容 |
|------|------|
| 概要 | ユーザーが指定したキーワードを含む全件を漏れなく抽出する |
| 入力 | 検索キーワード（1つ以上） |
| 出力 | キーワードを含む全件のリスト |

#### FR-005: 候補一覧表示

| 項目 | 内容 |
|------|------|
| 概要 | 検索結果をAdaptive Cardでタブ切り替え表示し、FAQ削除・シナリオ要修正フラグの操作UIを提供する |
| 入力 | 検索結果リスト |
| 出力 | Adaptive Card（Teams上に表示） |

**表示仕様:**

- シナリオとFAQを**タブ切り替え**で表示（`Action.ToggleVisibility`で実現）。混在表示はしない
- 各タブ内ではスコア降順で並べる
- 候補リストは**スクロールコンテナ**（Container の`maxHeight`プロパティ）で表示する。候補数が多くカードの全体サイズが長くなる場合でも、コンテナ内にスクロールバーが表示されカード自体は一定高さに収まる
- 万一候補数が多くカードサイズが28KBを超過する場合は、`Action.Execute`による**ページネーション**にフォールバックする（Bot側で件数に応じて出し分け）
- **シナリオタブ**: 各候補に「要修正」チェック（`Input.Toggle`）を配置。チェックした候補のみフラグを記録する
- **FAQタブ**: 各候補に選択チェック（`Input.Toggle`）を配置。複数選択→一括削除ボタンを表示する

**Adaptive Card レイアウト:**

**技術補足:**

- **スクロールコンテナ**: 各タブのContainer要素に`maxHeight: "400px"`を設定し、候補数が多い場合はスクロールバーを表示する。全候補が1枚のカード内に収まるため、選択状態の保持にBot側の一時保存は不要
- **28KB超過時のフォールバック**: Bot側でカードサイズを計算し、28KBを超える場合のみ`Action.Execute`によるページネーション（5件ずつ）に切り替える。ページネーション時はBot側（ConversationState）で選択状態を一時保持する
- タブ切り替えは`Action.ToggleVisibility`で`scenarioContainer`/`faqContainer`の表示を排他制御する
- `Action.Submit`と`Action.ToggleVisibility`は1アクションに同居できないため、データ送信は`Action.Execute`（Universal Actions）を使用する
- `Action.Execute`のレスポンスで新しいAdaptive Cardを返却することで、確認→完了の**Sequential Workflow**を実現する
- **非表示Inputの送信**: `ToggleVisibility`で非表示にしたコンテナ内の`Input.Toggle`も、`Action.Execute`押下時にすべての値が送信される。Bot側では`verb`（`confirmDeleteFaqs` / `saveNeedsUpdate`）に基づいて対象タブのInputのみ処理し、非表示タブのInputは無視する
- **操作完了後のUX**: Sequential Workflowの完了カードが表示された後、元の検索結果に戻るには再度テキスト入力が必要となる。PoCではこの動作を許容する

### 6.2 Azure Bot Service と Azure Web App の役割分担

Teams Botは2つのAzureリソースで構成される。

| リソース | 役割 | 説明 |
|---------|------|------|
| Azure Bot Service | チャネル管理 | TeamsチャネルとBot間のメッセージルーティング、認証、メッセージ変換を行うAzureマネージドサービス。Bot自体のコードは保持しない |
| Azure Web App (App Service) | Botバックエンド | Botのアプリケーションコード（TypeScript）をホストするWebサーバー。メッセージングエンドポイント（`https://<app-name>.azurewebsites.net/api/messages`）を公開し、Azure Bot Serviceからの受信メッセージを処理する |

Azure Bot Serviceはメッセージの中継と認証を担当し、実際のBot処理ロジック（テキスト入力受付、AI Search API呼び出し、Adaptive Card生成、Cosmos DB書き込み）はAzure Web App上で稼働する。

**SDK選定に関する注記:**

Bot Framework SDKは2025年12月でサポートが終了しており、Microsoft 365 Agents SDK（後継）への移行が推奨されている。Phase2 PoCではM365 Agents SDKでの実装を基本方針とし、技術的な制約がある場合はBot Framework SDK（TypeScript）を使用する。

### 7.1 データ構成

| データ種別 | 格納先 | 件数（概算） | 説明 |
|-----------|--------|------------|------|
| シナリオデータ | Cosmos DB `scenarios`コンテナ | 数百件 | チャットボットの会話シナリオ |

| 業務画像 | Blob Storage（Week 3追加） | 検証用数十件 | フロー図、手続き画面等のPNG/JPEG |
| 検索インデックス | Azure AI Search `impact-search-index` | 合計約3,500件＋画像 | シナリオ＋FAQ＋画像の統合インデックス |

**Cosmos DBコンテナ設計:**

| コンテナ名 | パーティションキー | 用途 | Indexer対象 |
|-----------|-----------------|------|-----------|
| `scenarios` | `/categoryId` | シナリオマスタデータ | ✓（Indexer A） |
| `faqs` | `/categoryId` | FAQマスタデータ | ✓（Indexer A） |
| `impactAssessments` | `/searchId` | 要修正フラグの判定記録 | ✗（検索インデックス不要） |

### 7.2 インデックス設計

シナリオ、FAQ、画像を同一インデックスに格納し、`dataType`フィールドで区別する。テキスト用と画像用の2つのベクトルフィールドを持つ。

**impact-search-index フィールド定義:**

| フィールド名 | 型 | 検索可能 | フィルタ可能 | ソート可能 | 説明 |
|-------------|-----|---------|-------------|----------|------|
| id | Edm.String | — | ✓ | — | 主キー |
| dataType | Edm.String | — | ✓ | — | `scenario` / `faq` / `image` |
| categoryId | Edm.String | — | ✓ | — | カテゴリID |
| categoryName | Edm.String | ✓ | ✓ | — | カテゴリ名 |
| title | Edm.String | ✓（ja.microsoft） | — | — | シナリオ名 / FAQ質問文 / 画像タイトル |
| content | Edm.String | ✓（ja.microsoft） | — | — | シナリオ本文 / FAQ回答文 / 画像説明 |
| combinedContent | Edm.String | ✓（ja.microsoft） | — | — | title + content（結合テキスト） |
| contentVector | Collection(Edm.Single) | ✓（vector） | — | — | 3,072次元（text-embedding-3-large） |
| imageVector | Collection(Edm.Single) | ✓（vector） | — | — | 1,024次元（Azure Vision multimodal）。Week 3追加 |
| keywords | Collection(Edm.String) | ✓ | ✓ | — | キーワード |
| updatedAt | Edm.DateTimeOffset | — | ✓ | ✓ | 更新日時 |
| isDeleted | Edm.Boolean | — | ✓ | — | 論理削除フラグ（Soft Delete） |

**注記:** テキストデータ（シナリオ/FAQ）は`contentVector`にのみベクトルを持ち、画像データは`imageVector`にのみベクトルを持つ。検索時は1回のクエリで両フィールドを同時指定可能（AI Searchが内部でRRFマージ）。

### 7.3 データフロー

**インデクシング（自動・定期）:**

```
[Indexer A: テキストデータ]
Cosmos DB → Indexer (1時間ごと)
  → AzureOpenAIEmbeddingSkill（text-embedding-3-large でベクトル生成）
  → contentVector フィールドに格納

[Indexer B: 画像データ]（Week 3追加）
Blob Storage → Indexer (1時間ごと)
  → Azure Vision multimodal embedding Skill（1,024次元ベクトル生成）
  → imageVector フィールドに格納
```

**検索（ユーザー操作時）:**

```
担当者 → Teams Bot → Azure Web App (Bot バックエンド)
  → [意味検索モードの場合]
      → AI Search REST API: ハイブリッド検索（原文テキスト）
      → ビルトインVectorizerが原文を自動ベクトル化
      → ベクトル検索 + キーワード検索 → RRF統合
      → Semantic Ranker でリランキング
      → rerankerScore ≥ 1.5 でフィルタ
      → dataTypeでシナリオ/FAQに分類 → タブ切り替え表示
  → [キーワード一致モードの場合]
      → AI Search REST API: search.ismatch で完全一致検索
      → dataTypeでシナリオ/FAQに分類 → タブ切り替え表示
  → Adaptive Card で候補を表示
```

**操作（ユーザーアクション時）:**

```
[FAQ削除]
担当者 → Adaptive Card（FAQタブでチェック → 削除ボタン）
  → Action.Execute → Azure Web App (Bot バックエンド)
  → Cosmos DB: faqs コンテナの該当ドキュメントを isDeleted = true に更新
  → 次回Indexer実行時にAI Searchインデックスから自動除外

[シナリオ要修正フラグ記録]
担当者 → Adaptive Card（シナリオタブでチェック → 保存ボタン）
  → Action.Execute → Azure Web App (Bot バックエンド)
  → Cosmos DB: impactAssessments コンテナに判定レコードを作成
```

### 7.4 データ保持期間

| データ種別 | 保持期間 | 備考 |
|-----------|---------|------|
| シナリオマスタ | 無期限 | マスタデータ |
| FAQマスタ | 無期限 | マスタデータ（削除はSoft Delete） |
| 影響判定記録（impactAssessments） | 無期限 | 要修正フラグの記録。FR-014で使用 |
| 検索インデックス | マスタと同期 | Indexerで自動管理 |

## 13. 付録

### 付録A: Phase1精度検証結果サマリ

| ケース | 改定タイプ | 検索方式 | Azure OpenAI結果 | 備考 |
|--------|----------|---------|-----------------|------|
| ① | 意味的関連（内容変更型） | ベクトル検索 | ほぼ全件検知 | — |
| ② | 意味的関連（内容変更型） | ベクトル検索 | ほぼ全件検知 | — |
| ③ | 意味的関連（内容変更型） | ベクトル検索 | ほぼ全件検知 | — |
| ④ | 意味的関連（内容変更型） | ベクトル検索 | ほぼ全件検知 | 1件未検知（画像内テキスト変更） |
| ⑤ | キーワード変更型 | ハイブリッド検索 | **100%検知** | AMLフィルター→ジープレックス |
| ⑥ | キーワード変更型 | ハイブリッド検索 | **100%検知** | スーパーカード(DC)→(MDC) |

**主要な知見:**

- ケース⑤⑥（名称変更型）はベクトル検索だけでは検知不可。キーワード完全一致検索との併用で100%検知を達成
- AIが人間の見落とし2件（小規模企業共済関連）を発見
- 原文検索とLLMクエリ拡張検索で精度に有意な差なし → 原文検索に統一する判断根拠
- 1件未検知（ケース④）: 画像内テキストの変更 → Week 3の画像ベクトル化検証で対応を検討

### 付録B: Phase2 PoC検証計画

**Week 1-2: テキスト検索基盤の構築・検証**

| # | 検証項目 | 成功基準 | 検証方法 |
|---|---------|---------|---------|
| 1 | ハイブリッド検索精度 | Phase1と同等以上のRecall（≥80%） | Phase1の6ケースをAzure環境で再検証 |
| 2 | Semantic Ranker有効性 | ベースライン（Rankerなし）より関連度向上 | 同一クエリでの有/無比較 |
| 3 | Indexer自動ベクトル化 | データ変更後1時間以内にインデックス反映 | データ追加 → Indexer実行 → 検索確認 |
| 4 | 差分更新の正確性 | 変更分のみが再ベクトル化される | Indexer実行ログで処理件数を確認 |
| 5 | キーワード完全一致検索 | 指定キーワードを含む全件が漏れなく抽出 | ケース⑤⑥で検証 |
| 6 | 検索レイテンシ | 1回の検索が10秒以内 | 10回の検索で平均・最大を計測 |
| 7 | Teams Bot連携 | 入力 → 検索 → Adaptive Card表示の一連動作 | エンドツーエンドテスト |
