## 1. 概要・目的

本文書は、事務改定影響調査システムの検索アーキテクチャを設計書として整理したものである。Azure AI Search のハイブリッド検索（BM25 + ベクトル + Semantic Ranker）の設計意図、パラメータ選定根拠、ローカル版（ChromaDB）との差分、チューニング経緯を記録する。

## 2. 用語集

| 用語 | 説明 |
|------|------|
| **HNSW** | Hierarchical Navigable Small World — 近似最近傍探索のグラフベースアルゴリズム |
| **m** | HNSW の各ノードからの双方向リンク数。大きいほど精度向上するがメモリ増加 |
| **efSearch** | HNSW 探索時の候補リストサイズ。大きいほど精度向上するが検索遅延増加 |
| **efConstruction** | HNSW グラフ構築時の候補リストサイズ。大きいほど構築品質向上 |
| **RRF** | Reciprocal Rank Fusion — 順位ベースのスコア統合。`score = 1/(rank + k)` |
| **BM25** | Best Matching 25 — TF-IDF ベースの全文検索スコアリング |
| **preFilter** | HNSW 探索中にフィルタを適用。再現率高いが小規模フィルタで遅い |
| **postFilter** | HNSW 探索後にフィルタを適用。高速だが結果が k 件未満になりうる |
| **Semantic Ranker** | Microsoft 多言語モデルによる L2 リランキング。L1 結果の上位50件を再評価 |
| **Score-based fusion** | 生スコアの線形結合。ローカル版方式 |
| **Rank-based fusion** | 順位の逆数で統合。Azure RRF 方式 |

```
                                       │
                       maintenance-skillset ──→ Azure OpenAI
                       (combinedContent → 3,072次元ベクトル)
                                       │
                                       ▼
                             maintenance-search-index          searchSingle()
                             (15フィールド、21,047件)    ←──  agent.ts
                                       ▲
                                       │
faqs コンテナ                cosmos-faqs-ds (DataSource)
 ├── smile (8,679件)         ──→  maintenance-faqs-indexer
 ├── sousoku (4,000件)            ├── fieldMappings (11フィールド)
└── yokin (6,055件)              └── schedule: 10分ごと（PT10M）
```

**検索フロー（1リクエストあたり）:**

```
ユーザー → Teams チャット入力
  ↓
モード選択カード: 業務分野を単一選択 + 表示件数選択（10〜100件）
  ↓
Bot (TypeScript) → 選択された1カテゴリに対して searchSingle() を実行
  ↓
各 searchSingle() 内（AI Search API 1回コール）:
  ├── BM25 テキスト検索 (ja.microsoft アナライザ)
  ├── Vectorizer → クエリベクトル生成 (text-embedding-3-large)
  ├── HNSW ベクトル検索 (cosine)
  ├── RRF (Reciprocal Rank Fusion) でスコア統合
  └── Semantic Ranker で上位50件を再ランキング（`@search.rerankerScore` を優先採用）
  ↓
検索結果を関連度順に整形 → Adaptive Card (動的ページサイズ、サイズ上限25KB)
```

### ローカル版（ChromaDB）

```
ユーザー → Excel バッチ入力
  ↓
Python (Searcher)
  ├── Sudachi 形態素解析 → キーワード抽出
  ├── Embedding API → クエリベクトル生成
  ├── ChromaDB (ローカル) → ベクトル検索 (cosine)
  ├── KeywordSearchEngine → Jaccard 類似度計算
  ├── 加重スコア統合 (0.9×vector + 0.1×keyword)
  └── Excel 出力 (top_k=4)
```

**主要な違い:** ローカル版はカテゴリ別 ChromaDB コレクション（自動分離）+ スコアベース線形結合。クラウド版は1インデックス + categoryId フィルタ + 順位ベース RRF 統合。

### 4-B. combinedContent のフォーマット

**シナリオ:**
```
"分類: {Lv1 > Lv2 > ... > Lv(n-2)} | 質問: {Lv(n-1)} | 回答: {Lv(n)}"

```

### 4-C. combinedContent の構成要素決定ロジック

#### シナリオの右→左スキャン（ローカル版 / クラウド版 共通）

```

結果:

  title   = "/預金関連/普通預金/新規口座開設/本人確認"
  combined = "分類: 預金関連 > 普通預金 > 新規口座開設 | 質問: 本人確認 | 回答: 運転免許証の場合"
```

## 5. テキスト検索

### 5-A. トークン化

| 項目 | ローカル版 (Sudachi) | クラウド版 (ja.microsoft) |
|------|-------------------|----------------------|
| エンジン | Sudachi (SplitMode.C) | Microsoft 日本語アナライザ (MeCab ベース) |
| 辞書 | sudachi-dictionary-full | Microsoft 独自辞書 |
| 分かち書き精度 | 高（銀行用語に強い） | 高（一般用語に強い） |
| カスタム辞書 | Sudachi ユーザー辞書追加可能 | 不可（Azure 管理） |

両者とも日本語形態素解析としては十分な品質。Sudachi は「取引時確認」「預り物件」等の複合語を1トークンとして認識する精度がやや高いが、BM25 は部分一致でもスコアが付くため実用差は小さい。

### 5-B. スコア計算

| 項目 | ローカル版 (Jaccard) | クラウド版 (BM25) |
|------|-------------------|----------------|
| アルゴリズム | Jaccard 類似度（集合の共通率） | BM25 (TF-IDF 拡張 + 文書長正規化) |
| 文書長正規化 | なし | あり（b=0.75 で長い文書のスコアを抑制） |
| 値域 | 0.0〜1.0 | 0.0〜∞（上限なし、相対スコア） |
| 検索対象フィールド | combined_text（1フィールド） | title, content, keywords（**3フィールド**、searchFields 明示指定） |

**精度への影響:**
- BM25 は IDF（逆文書頻度）を考慮するため、「口座」のような高頻度語よりも「AMLフィルター」のような低頻度語を重視する。Jaccard にはこの概念がない
- クラウド版 は 3 フィールド横断検索（title, content, keywords）なので、title に含まれなくても keywords や content で拾える。再現率は クラウド版 の方が高い

### 5-C. キーワードの扱い

**ローカル版:** Sudachi 形態素解析でクエリから名詞を抽出（品詞重み付け + 位置重み）→ Jaccard 係数で文書と比較（クエリ主導）。

**クラウド版:** 明示的なキーワード抽出なし。ドキュメント側に `keywords` フィールドを事前格納し、BM25 で検索（ドキュメント主導）。

| データ種別 | keywords の決定ロジック | 例 |
|-----------|----------------------|-----|
| シナリオ | 階層パスの各レベルテキスト | `["預金関連", "普通預金", "新規口座開設", "本人確認"]` |
| FAQ (タグあり) | タグ文字列から `Lv\d+:\s*` でパース | `["営業事務", "預り物件管理システム"]` |
| FAQ (タグなし) | 空配列 | `[]` |

ローカル版 の品詞フィルタ（名詞のみ）と位置重み付けは クラウド版 にはないが、BM25 の IDF 重み付けが部分的に補完する。

## 6. スコア統合 — RRF

### 6-A. ローカル版: スコアベース線形結合

```
final_score = 0.9 × cosine_similarity + 0.1 × keyword_similarity
```

- 両方とも 0〜1 に正規化されたスコア → 直接加算可能
- スコア差の保存あり（cosine 0.95 vs 0.90 = 0.05差が反映される）
- weight を変えて A/B テスト可能

### 6-B. クラウド版: 順位ベース RRF (Reciprocal Rank Fusion)

```
RRF_score(文書) = weight × 1/(vector_rank + 60) + 1.0 × 1/(BM25_rank + 60)
```

- `rank`: 各結果セット内での順位 (1, 2, 3, ...)
- `60`: Azure AI Search の固定パラメータ (k=60、変更不可)
- `weight`: ベクトルクエリの RRF 乗数（現在 **4.5**）

**計算例:**
```
文書A: vector 1位, BM25 10位
  → 4.5 × 1/(1+60) + 1.0 × 1/(10+60) = 0.0738 + 0.0143 = 0.088

文書B: vector 5位, BM25 1位
  → 4.5 × 1/(5+60) + 1.0 × 1/(1+60) = 0.0692 + 0.0164 = 0.086

文書C: vector 3位, BM25 3位
  → 4.5 × 1/(3+60) + 1.0 × 1/(3+60) = 0.0714 + 0.0159 = 0.087

  → 結果: A > C > B  (ベクトル検索が優位だが BM25 も寄与)
```

### 6-C. 核心的な違い

| 特性 | ローカル版 (Score-based) | クラウド版 (Rank-based RRF) |
|------|----------------------|--------------------------|
| **入力** | 生スコア (cosine=0.95 など) | 順位 (1位, 2位, 3位...) |
| **スコア差の保存** | あり (0.95 vs 0.90 = 0.05差) | **なし** (1位 vs 2位 のみ) |
| **正規化の必要性** | 両方0〜1なので不要 | 順位なので自動的に正規化 |
| **重みの意味** | スコア空間での割合 | RRF 逆順位スコアの乗数 |

**結論:** ローカル版 の `0.9:0.1` をそのまま クラウド版 の `weight` に変換しても同じ効果にはならない。ただし「ベクトル検索を強く重視する」という意図は同じ方向性。weight=4.5 はベクトル重視を維持しつつ BM25 の寄与も残すバランス。

## 7. フィルタ設計

### 7-A. preFilter と postFilter

Azure AI Search では、ベクトル検索にフィルタ（例: `categoryId eq 'smile'`）を適用する方法が2種類ある。

**preFilter（現在使用中）:**

```
[全21,047件のHNSWグラフ]
        │
        ▼ HNSW グラフを走査しながらフィルタを同時適用
        │  → categoryId='smile' に合致するノードだけを候補として探索
        │  → k件の候補が見つかるまでグラフを展開し続ける
        │
        ▼ 結果: フィルタ済みの k件（確実に k件返る）
```

- **メリット**: 必ず k件のフィルタ済み結果が返る（再現率が高い）
- **デメリット**: フィルタ後の候補が少ないと（例: torikaku=105/21,047件 = 0.5%）、HNSW グラフの大部分を走査する必要があり遅くなる。m が小さいグラフではフィルタ後に到達できない孤立ノードが発生し、精度が低下する

**postFilter:**

```
[全21,047件のHNSWグラフ]
        │
        ▼ Step 1: フィルタなしで HNSW 探索 → 上位 k件を取得
        │
        ▼ Step 2: k件に対してフィルタを適用 → 合致しない文書を除外
        │
        ▼ 結果: k件以下（フィルタで除外された分だけ減る）
```

- **メリット**: HNSW 探索は高速
- **デメリット**: 上位 k件にフィルタ対象カテゴリの文書が少ないと、結果が k件未満になる

### 7-B. 小カテゴリ問題と対策

torikaku（105件）や souzoku（269件）のような小カテゴリでは、preFilter + m=10 のグラフでも精度低下が発生しうる。

**対策: exhaustive（全件探索）の適用**

```typescript
const SMALL_CATEGORY_IDS = new Set(["torikaku", "souzoku"]);
const useExhaustive = SMALL_CATEGORY_IDS.has(categoryId);
```

小カテゴリは件数が少ないため全件探索でもパフォーマンス影響はなく、精度が確実に保証される。

### 7-C. ローカル版 との比較

| 項目 | ローカル版 | クラウド版 |
|------|---------|---------|
| データ分割 | カテゴリ × タイプ別コレクション | 1インデックス + categoryId フィルタ |
| フィルタの必要性 | 不要（コレクション分離） | 必要（preFilter） |
| 小カテゴリの精度 | 高（専用コレクション内の密なグラフ） | exhaustive で補完 |

## 8. Semantic Ranker

### 8-A. 仕組み

```
L1 ランキング (BM25 + HNSW + RRF)
  → 上位50件を取得
  → Microsoft 多言語 Transformer モデルで再スコアリング
  → @search.rerankerScore (0.0〜4.0) で並び替え
```

- Bing 検索から移植された多言語ディープラーニングモデル
- 日本語を含む複数言語で NDCG 改善が報告されている
- ただし L1 の結果が悪ければ、Semantic Ranker でも救えない
- **上位50件制約**: L1 の上位50件のみが再ランキング対象（固定、変更不可）

### 8-B. 現在の状態

**有効**（`queryType: "semantic"`, `semanticSearchOptions: { configurationName: "semantic-config" }`）

L1（RRF）→ L2（Semantic Ranker）の2段パイプライン。当初は精度向上が確認されず廃止していたが、L1 の改善（HNSW m=10、weight 調整、exhaustive 適用）後に再有効化し、現在は有効のまま運用。実装では semantic モード時に `@search.rerankerScore` を優先して最終順位と表示用の関連度に使用する。

### 8-C. Semantic Config のフィールド設定

```json
{
  "titleField": { "fieldName": "title" },
  "prioritizedContentFields": [
    { "fieldName": "content" },
    { "fieldName": "combinedContent" }
  ],
  "prioritizedKeywordsFields": [
    { "fieldName": "keywords" }
  ]
}
```

```typescript
  filter,                            // "isDeleted eq false and dataType eq '...' and categoryId eq '...'"

```

### 9-C. キーワード検索（searchSingle — keyword モード）

```typescript
const options = {
  queryType: "full" as const,
  searchFields: ["title", "content", "keywords"],
  select: ["id", "dataType", "categoryId", "categoryName", "title", "content", "order"],
  top: topN,
  filter,
};
```

**注記:** 本モードは「完全一致検索」ではなく、`title` / `content` / `keywords` を対象にした語句ベースの全文検索である。業務用語や略称を語単位で拾う用途を想定し、文字列の途中一致（任意 substring）は対象外。

### 9-D. バリデーション

```typescript
// カテゴリID: ホワイトリスト（Set）で検証（agent.ts）
const VALID_SCENARIO_IDS = new Set(SCENARIO_CATEGORIES.map((c) => c.id));
const VALID_FAQ_IDS = new Set(FAQ_CATEGORIES.map((c) => c.id));

// topN: 10〜100 に制限（agent.ts）
function extractSafeTopN(data, targetType): number {
  let raw = extractNumber(data, primaryKey, -1);
  if (raw < 0) raw = DEFAULT_TOP_N;  // 30
  return Math.min(Math.max(raw, 10), 100);
}
```

検索カードはシナリオタブ / FAQタブで分離し、各タブ内でカテゴリを**単一選択**してから検索を実行する。

### 10-C. 結果表示

- 検索結果は選択した1カテゴリ・1データ種別（シナリオまたはFAQ）について、関連度順にページネーション表示する
- 結果カードでは関連度を表示し、semantic モードでは `rerankerScore` を優先採用する
- アクションボタン（「要修正を保存」「選択したFAQを削除」）は結果内容に応じて両方表示
- 1ページあたりの表示件数は動的（初期値 `ITEMS_PER_PAGE=100`、Adaptive Card サイズ上限 25KB に収まるまで二分探索で縮小）

## 11. チューニング経緯

### 11-A. 初期課題（クラウド版 構築時に特定）

クラウド版 の検索精度が ローカル版 より低い原因として、以下の11項目を特定した。

| # | 要因 | ローカル版 | クラウド版 (初期) | 影響度 |
|---|------|---------|---------------|--------|
| 1 | HNSW m | 16 (ChromaDB デフォルト) | **4** (Azure 最小値) | 大 |
| 2 | データ分割 | カテゴリ別コレクション | 1インデックス + フィルタ | 大 |
| 3 | スコア統合方式 | Score-based 線形結合 | Rank-based RRF | 中 |
| 4 | フィルタ方式 | フィルタ不要 | preFilter（HNSW断片化リスク） | 大（小カテゴリ） |
| 5 | テキスト検索 | Sudachi + Jaccard | BM25 (ja.microsoft) | 中 |
| 6 | キーワード抽出 | Sudachi 形態素解析で上位5語 | なし（BM25 に依存） | 小 |
| 7 | Semantic Ranker | なし（ローカル版 にも存在しない） | 無効 | — |
| 8 | weight 値 | 0.9（score-based） | 9.5（RRF 乗数、BM25 寄与ほぼゼロ） | 中 |
| 9 | Azure m 上限 | m=16 可能 | m=10 が上限 | 中 |
| 10 | カテゴリ別検索のスコア非互換 | 不要 | 独立 RRF のスコア直接比較 | 中 |
| 11 | RRF のスコア差損失 | cosine 差を保存 | 順位のみ使用 | 小〜中 |

### 11-B. 実施した対策と結果

| 対策 | 変更内容 | 結果 |
|------|---------|------|
| HNSW m 変更 | m=4 → **m=10**（Azure 上限） | グラフ密度向上、再現率改善 |
| efSearch 変更 | efSearch=500 → **efSearch=1000** | 探索精度向上 |
| weight 調整 | 9.5 → 5.0 → **4.5** | BM25 の寄与を回復しつつベクトル優位を維持 |
| exhaustive 適用 | なし → **torikaku, souzoku** に適用 | 小カテゴリの精度低下を解消 |
| vectorFilterMode 明示 | 未指定 → **preFilter 明示** | 挙動の明確化 |
| keywords フィールド改善 | FAQ に質問文・回答文を追加、`ja.microsoft` アナライザ適用 | BM25 の差別化改善 |
| Semantic Ranker 有効化 | queryType: "simple" → **"semantic"** | L1 改善後に再有効化、順位の微調整効果あり |
| Semantic Ranker反映 | `@search.score` のみ利用 → **`@search.rerankerScore` 優先** | Semantic Ranker の最終順位をUIに反映 |
| カテゴリ選択UI変更 | 複数選択 → **単一選択** | 独立クエリ間のスコア比較問題を回避 |
| インデックス再作成 | PUT 更新 → **DELETE + PUT 再作成** | m 変更はインデックス再作成が必須 |

### 11-C. LLM クエリ拡張

ローカル版 で3戦略（Original / LLMEnhanced / MultiStage）を実装したが、評価結果として精度向上が確認されなかったため クラウド版 では非採用。
