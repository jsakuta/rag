## 1. 概要

本ドキュメントは、チャットボットのシナリオ（FAQ）情報の設計仕様を定義します。

**シナリオの目的:**
- ユーザーからの問い合わせに対して、FAQ形式で回答を提供
- 階層構造による段階的な情報提供
- ジャンプリンクによる関連FAQ間の連携

**データフロー:**
```
SharePoint Excel（原本）
  ↓ アップロード
Cosmos DB（最新版のみ）
  ↓ ダウンロード
Excel（エクスポート）
```

**技術仕様:**
- データベース: Azure Cosmos DB
- 原本管理: SharePoint Online
- タイムゾーン: 日本標準時（JST, UTC+9）統一
- 削除方式: 物理削除（最新版のみ保持）
- 最大階層数: 30階層

## 2. 共通仕様

### 2.1. ID生成ルール

#### FAQ ID

**形式:** `FAQ-{カテゴリID}-{8文字ハッシュ}`

**生成方法:**
```typescript
function generateFaqId(categoryId: string, path: string): string {
  const hash = crypto
    .createHash('sha256')
    .update(`${categoryId}::${path}`, 'utf8')
    .digest('hex')
    .substring(0, 8);
  
  return `FAQ-${categoryId}-${hash}`;
}
```

**例:**
```typescript
generateFaqId(
  "BIZ-A1B2C3",
  "/科目別に探す/保証/保証人の免除について知りたい/保証免除依頼書の徴求要否/取引別根保証/当貸の期限と同時に期日が到来し、保証人を免除したい"
)
// → "FAQ-BIZ-A1B2C3-7f8a9c2d"
```

**特徴:**
- **決定論的**: 同じcategoryIdとFAQ階層パス（path）なら常に同じfaqIdが生成される
- **カテゴリ識別**: カテゴリIDを含むため、一目でどのカテゴリのFAQか分かる
- **衝突回避**: `categoryId`を区切りとして含めることで、異なるカテゴリで同じFAQ階層パスを持つ場合も別IDになる

**重要:**
- FAQ階層パス（path）が同じなら必ず同じfaqIdが生成される
- 回答内容を変更してもfaqIdは変わらない
- FAQ階層パス（path）を変更すると別のfaqIdになる（新規FAQ扱い）

---

### 2.2. FAQ IDの粒度方針

本システムでは、**各階層パスに対して個別のFAQ ID**を生成します。

#### 設計方針

| 観点 | 本システムの方針 | 説明 |
|:---|:---|:---|
| **FAQ IDの粒度** | 各階層パスごとに生成 | 途中階層にも末端階層にも個別のFAQ IDを割り振る |
| **途中階層の扱い** | FAQとして管理 | 概要説明文を持つコンテンツとして扱う |

#### 具体例

```
/保証人の免除について知りたい           → FAQ-BIZ-XXX-aaaa1111（概要説明あり）
    └── /公正証書あり                   → FAQ-BIZ-XXX-bbbb2222（概要説明あり）
        └── /免除します                 → FAQ-BIZ-XXX-cccc3333（最終回答）
```

上記の例では、3つの異なる階層パスに対して、それぞれ異なるFAQ IDが生成されます。

#### 採用理由

1. **途中階層にも概要説明がある**: 本システムでは途中階層にも回答テキスト（概要説明文）があり、それ自体がコンテンツとして価値を持つ
2. **シナリオ利用ログとの整合性**: シナリオ利用ログでは「1クリック=1ドキュメント」方式を採用しており、各階層のFAQ IDをログに記録することで階層別の利用状況を分析可能

#### シナリオ利用ログとの関係

シナリオ利用ログでは、利用者がクリックした各階層のFAQ IDと回答テキスト（スナップショット）を記録します。これにより以下の分析が可能です：

- **階層別の閲覧数**: どの階層がよく閲覧されているか
- **離脱率**: どの階層で利用者が離脱しているか
- **経路分析**: 利用者がどの経路を辿って最終回答に到達したか

**関連**: シナリオ利用ログの記録方式については「ログ設計書」を参照。

### 2.3. タイムゾーン仕様

すべての日時データは日本標準時（JST, UTC+9）で統一します。

#### JSON（Cosmos DB）
- **形式**: ISO 8601形式（タイムゾーン付き）
- **例**: `"2025-11-12T18:30:00.000+09:00"`

#### Excel出力
- **形式**: `YYYY-MM-DD HH:mm:ss`
- **タイムゾーン**: JST（表記なし、暗黙的にJST）
- **例**: `2025-11-12 18:30:00`

#### 変換関数

```typescript
function toJSTISO8601(date: Date): string {
  const jstDate = new Date(date.toLocaleString('en-US', { timeZone: 'Asia/Tokyo' }));
  const offset = '+09:00';
  
  const year = jstDate.getFullYear();
  const month = String(jstDate.getMonth() + 1).padStart(2, '0');
  const day = String(jstDate.getDate()).padStart(2, '0');
  const hour = String(jstDate.getHours()).padStart(2, '0');
  const minute = String(jstDate.getMinutes()).padStart(2, '0');
  const second = String(jstDate.getSeconds()).padStart(2, '0');
  const ms = String(jstDate.getMilliseconds()).padStart(3, '0');
  
  return `${year}-${month}-${day}T${hour}:${minute}:${second}.${ms}${offset}`;
}
```

#### 重要な注意点
- Cosmos DBの`_ts`フィールド（自動生成）はUNIX timestamp（UTC）です
- `_ts`は内部管理用のみで使用し、業務データの分析には`createdAt`/`updatedAt`フィールドを使用してください

### 2.4. データ保持方式

#### FAQの削除方式：物理削除

**方針:**
- FAQは**物理削除**を採用します
- 削除されたFAQはCosmos DBから完全に削除されます
- 論理削除フラグ（`status`フィールド）は使用しません

**理由:**
1. **要件定義書の規定**: 「Cosmos DBにはシナリオ（FAQ）の最新版のみを保持」と明記
2. **ストレージコストの最適化**: 削除されたFAQを保持する必要がない
3. **データの単純性**: 論理削除フラグを管理する複雑さを回避

**カテゴリとの違い:**
- **カテゴリ**: 論理削除（永久保持）
- **FAQ**: 物理削除（最新版のみ）

**削除後のデータ保持:**
- **7日以内**: Cosmos DBの継続的バックアップから復元可能
- **8日以降**: SharePointのExcelバージョン履歴から手動復旧が必要
- **過去ログ**: 利用ログに回答内容が保存されているため、分析は可能

## 3. JSON設計（Cosmos DB）

### 3.1. スキーマ定義

```typescript
/**
 * シナリオドキュメント（Cosmos DB）
 */
interface ScenarioDocument {
  id: string;                    // 例: "scenario-BIZ-A1B2C3"
  type: "scenario";
  categoryId: string;            // 例: "BIZ-A1B2C3"
  categoryName: string;          // 例: "店頭業務/スマイル/新規・諸届・喪失"（大分類/中分類/小分類）
  lastUpdated: string;           // ISO 8601形式（JST）
  faqs: FAQ[];
  _ts?: number;
}

/**
 * FAQ（よくある質問と回答）
 */
interface FAQ {
  faqId: string;                 // 例: "FAQ-BIZ-A1B2C3-7f8a9c2d"
  path: string;                  // FAQ階層パス 例: "/科目別に探す/保証/保証人の免除について知りたい"
  order: number;                 // 表示順（Excelの行番号、1から開始）
  answer: string;                // 回答テキスト（概要説明または最終回答）※必須、空文字列不可
  isFinalAnswer: boolean;        // true: 最終回答（子ノードなし）, false: 概要説明（子ノードあり）
  linkedFaqIds: string[];        // 内部リンク先のfaqIdリスト（FAQへのジャンプのみ、カテゴリリンクは含まない）
  createdAt: string;             // ISO 8601形式（JST）
  updatedAt: string;             // ISO 8601形式（JST）
}

/**
 * orderフィールドの生成ルール:
 * - Excelの行番号（ヘッダー行を除く、1始まり）がそのままorderになる
 * - 例: Excel2行目（データ1行目）→ order: 1
 * - 同じパスを持つFAQが複数行に分かれることはない（1FAQ = 1行）
 */
```

**重要:**
- `path` は**FAQ階層パス**を表し、FAQの階層構造を「/」で区切った文字列として格納します
- **pathには「質問/選択肢」のみが含まれ、「回答テキスト」は含まれません**
  - 例: Lv6が質問、Lv7が回答の場合 → pathはLv6まで（`/Lv1/.../Lv6`）
- FAQ階層パスが同じなら必ず同じfaqIdが生成される（決定論的）
- 回答内容を変更してもfaqIdは変わらない
- FAQ階層パスを変更すると別のfaqIdになる（新規FAQ扱い）

#### isFinalAnswerの判定ロジック

`isFinalAnswer`は**子ノードの有無**で機械的に判定します（テキストの長さや内容は無関係）。

**判定ルール:**
```typescript
function determineFinalAnswer(currentRow: ExcelRow, allRows: ExcelRow[]): boolean {
  // 現在の行の最深階層レベルを取得
  const currentDepth = getDeepestLevel(currentRow);
  
  // 次の行以降で、同じ親パスを持ち、かつより深い階層にテキストがあるか確認
  for (const nextRow of allRows) {
    if (nextRow.order <= currentRow.order) continue;  // 自分より前の行はスキップ
    
    // 同じ親パス（currentDepth - 1 まで一致）を持つか
    if (!hasSameParentPath(currentRow, nextRow, currentDepth - 1)) continue;
    
    // 次の行がより深い階層にテキストを持つ場合、子ノードが存在する
    if (getDeepestLevel(nextRow) > currentDepth) {
      return false;  // 概要説明（子ノードあり）
    }
  }
  
  return true;  // 最終回答（子ノードなし = 末端ノード）
}
```

**具体例（セクション4.3のExcelデータ例を参照）:**

| 行 | Lv3 | Lv4 | Lv5 | Lv6 | Lv7 | isFinalAnswer | 理由 |
|:-:|:---|:---|:---|:---|:---|:---:|:---|
| 1 | 保証人の免除について知りたい | 概要説明文... | | | | **false** | 行2以降でLv4「保証免除依頼書の徴求要否」があり、Lv5以降も続く（子ノードあり） |
| 2 | 保証人の免除について知りたい | 保証免除依頼書の徴求要否 | 概要説明文... | | | **false** | 行3でLv5「取引別根保証」を持つ（子ノードあり） |
| 3 | 保証人の免除について知りたい | 保証免除依頼書の徴求要否 | 取引別根保証 | 概要説明文... | | **false** | 行4でLv6・Lv7を持つ（子ノードあり） |
| 4 | 保証人の免除について知りたい | 保証免除依頼書の徴求要否 | 取引別根保証 | 当貸の期限と同時に... | 回答文 | **true** | これ以降に同じ親パスでより深い階層なし（末端） |

**重要:** すべての行の最右列には必ず「回答テキスト」または「概要説明文」が入ります。選択肢のみで終わる行は存在しません。

**注:** 上記の表はExcel列のLv3〜Lv7を抜粋しています。Lv1（科目別に探す）とLv2（保証）は省略しています。

### 3.2. linkedFaqIdsの解決と管理

回答テキスト内の内部リンク（`[表示テキスト](/FAQ階層パス)`形式）から、リンク先のfaqIdを抽出して`linkedFaqIds`配列に格納します。

**解決タイミング:** Excelアップロード時（事前解決）

`linkedFaqIds`はExcelアップロード時に一度だけ解決され、Cosmos DBに保存されます。
FAQ閲覧時には`linkedFaqIds`に格納済みのfaqIdを使用してリンク先の存在確認を行います。

**処理フロー（Excelアップロード時）:**
1. 回答テキストから内部リンクを抽出（正規表現: `\[([^\]]+)\]\((\/[^)]+)\)`）
2. リンク種別を判定:
   - `/categories/` で始まる → **カテゴリリンク**（linkedFaqIdsには追加しない）
   - それ以外の `/` で始まる → **FAQリンク**（linkedFaqIdsに追加対象）
3. FAQリンクの場合、全カテゴリのシナリオを横断検索してFAQ階層パスに一致するFAQを特定
4. 見つかったFAQのfaqIdを`linkedFaqIds`に追加

**重要: linkedFaqIdsに格納されるもの**
- **含まれる**: FAQへの内部リンク（`[表示テキスト](/FAQ階層パス)` 形式）のfaqId
- **含まれない**: カテゴリリンク（`[表示テキスト](/categories/BIZ-XXXXXX)` 形式）
- **含まれない**: 外部リンク（`https://` で始まるURL）

**例:**
```
回答テキスト:
  "詳細は以下を参照してください。
   [相続手続き](/手続き別/相続手続き/保証免除)
   [相続窓口へ](/categories/BIZ-M4N7K2)
   [マニュアル](https://sharepoint.com/docs/manual.pdf)"

linkedFaqIds: ["FAQ-BIZ-M4N7K2-9i0j1k2l"]  // FAQリンクのみ
// カテゴリリンクと外部リンクはlinkedFaqIdsには含まれない
```

#### FAQ削除時のlinkedFaqIdsの扱い

**重要:** 削除されたFAQを参照している他のFAQの`linkedFaqIds`は**更新しません**。

**理由:**
- リンク切れを検出するために、削除されたFAQ IDを保持する必要がある
- 定期的な整合性チェックでリンク切れを検出し、管理者に通知する

**リンク切れの検出:**
```typescript
async function checkLinkIntegrity() {
  const allScenarios = await getAllScenarios();
  const brokenLinks: BrokenLink[] = [];
  
  for (const scenario of allScenarios) {
    for (const faq of scenario.faqs) {
      for (const linkedFaqId of faq.linkedFaqIds) {
        // リンク先のFAQが存在するか確認
        const targetFaq = await findFaqById(linkedFaqId);
        
        if (!targetFaq) {  // 物理削除済み
          brokenLinks.push({
            sourceFaqId: faq.faqId,
            sourceFaqPath: faq.path,
            targetFaqId: linkedFaqId,
            reason: "FAQ not found (deleted)"
          });
        }
      }
    }
  }
  
  return brokenLinks;
}
```

### 3.3. FAQ削除の動作

#### カテゴリ削除時
- カテゴリが論理削除される（`status: "deleted"`）
- カテゴリ配下のシナリオドキュメント（FAQを含む）は**物理削除**される
- 利用者側のUIでは、削除されたカテゴリは表示されない

#### FAQ個別削除時
- FAQは**物理削除**される（Cosmos DBから完全に削除）
- 削除から7日以内であれば、Cosmos DBのポイントインタイムリストアで復元可能
- 8日以上経過した場合、SharePointのExcelバージョン履歴から手動復旧が必要

#### 削除後のデータ保持

| 期間 | データ所在 | 復元方法 |
|:---|:---|:---|
| **7日以内** | Cosmos DBバックアップ | ポイントインタイムリストアで自動復元 |
| **8日〜5年** | SharePointバージョン履歴 | Excelファイルをダウンロードして再アップロード |
| **5年以降** | - | 復元不可 |
| **過去ログ** | シナリオ利用ログ | 回答内容が保存されているため分析可能 |

---

**【補足】物理削除を採用する理由**

FAQは物理削除を採用していますが、以下の理由により運用・分析上の問題はありません

1. **過去ログでの追跡性**: シナリオ利用ログに`faqAnswer`（回答全文）と`faqPath`（階層パス）を保存しているため、FAQ削除後も分析可能
2. **配列肥大化の防止**: 論理削除を採用すると、1カテゴリあたり500件のFAQ配列に削除済みFAQが蓄積し、ドキュメントサイズが増大（5年で約12%増加）
3. **SharePointバックアップ**: Excelバージョン履歴（5年保持）から復元可能
4. **リンク整合性**: 削除時に参照元FAQを警告表示し、利用者には「このFAQは削除されました」と表示される

**カテゴリとの設計思想の違い**: カテゴリは件数が少なく（約70件）、単独ドキュメントのため論理削除で問題ないが、FAQは件数が多く（カテゴリあたり500件、総数約35,000件）、配列要素のため物理削除が適切。

## 4. Excel設計（入力）

### 4.1. ファイル名規則

#### アップロード（入力）

```
scenario_{カテゴリID}_{大分類}_{中分類}_{小分類}.xlsx
```

**例:**
```
# 小分類がある場合
scenario_BIZ-A1B2C3_店頭業務_スマイル_新規・諸届・喪失.xlsx

# 小分類がない場合
scenario_BIZ-Z9Y8X7_店頭業務_取引時確認.xlsx
```

**カテゴリ名の規則:**
- **小分類がある場合**: `{大分類}_{中分類}_{小分類}`
- **小分類がない場合**: `{大分類}_{中分類}`

**重要:**
- **ファイル名のカテゴリID部分(BIZ-XXXXXX)は変更厳禁**
- ダウンロード時のタイムスタンプ（`_YYYYMMDD_HHMMSS`）は削除を推奨
- システムはカテゴリID部分のみで判定するため、カテゴリ名部分の変更は可能だが推奨しない

---

### 4.2. 列構造

```
Lv1 | 文字数 | Lv2 | 文字数 | Lv3 | 文字数 | ... | Lv30 | 文字数
```

- **階層列**: Lv1～Lv30（最大30階層）
- **文字数列**: 各階層の後に挿入（管理者用の参考情報、システムは読み飛ばす）
- **合計列数**: 60列（30階層 × 2）

#### 文字数列について

文字数列は**管理者の編集作業を補助するための列**です。

**運用方法:**
- **空欄のままでOK**: システムは文字数列を読み飛ばすため、入力は不要です
- **任意で数式を設定**: 管理者が文字数を確認したい場合、Excel関数（例: `=LEN(A2)`）を設定可能
- **手入力も可**: 目視確認用に手動で入力しても問題ありません

**注意:** 文字数列の値はCosmos DBには保存されません。

**カテゴリIDの確認方法:**
リンク先に指定するカテゴリID（例: `BIZ-A1B2C3`）は、**業務カテゴリ管理用Excel（categories.xlsx）の右端の列（カテゴリID列）**で確認してください。

### 4.5. アップロード時の検証仕様

管理者がチャット画面にExcelファイルをアップロードすると、ボットは以下の手順で検証と更新を行います。

#### 1. ファイル名による自動判別

ファイル名のプレフィックスとID部分を解析し、更新対象を特定します。

- **プレフィックス:** `scenario_`
- **カテゴリID:** `BIZ-XXXXXX`形式のIDを抽出
- **判定:** 上記2条件を満たす場合、「シナリオ更新」として処理

#### 2. 差分の検出と確認画面

アップロードされたファイルと現在のデータベースを比較し、差分（追加・更新・削除）を検出します。
その後、更新を実行する前に確認カードを表示します。

**仕様の詳細については、『チャットボット管理・運用ガイドブック』の「2.7. ファイルアップロードの共通仕様」を参照してください。**

**シナリオ固有の検証事項:**
- **リンク切れチェック**: 削除されるFAQを参照している他のFAQがないか確認します。参照がある場合は警告を表示します。
- **ファイル名整合性**: ファイル名に含まれるカテゴリIDと、Excel内のデータに矛盾がないか確認します。

**アップロード時のファイル名については、セクション4.1を参照してください。**

### 5.2. 出力形式

**フォーマット:**
「4. Excel設計（入力）」で定義された形式と基本的に同一ですが、列数に違いがあります。

**列数について:**
- **入力時**: 最大30階層×2列（60列）をサポート
- **出力時**: 実際のデータの最深階層までの列のみ出力

**例:**
シナリオの最深階層がLv7の場合：
```
Lv1 | 文字数 | Lv2 | 文字数 | ... | Lv7 | 文字数
```
→ 14列のみ出力（Lv8以降は出力されない）

**理由:**
- **可読性向上**: 不要な空列を排除し、管理者が編集しやすくなる
- **ファイルサイズ最適化**: 必要な列数のみでExcelファイルを軽量化
- **アップロードに影響なし**: システムは入力時に存在する列のみを処理するため、列数が少なくても問題なし

**用途:**
- 現在のシナリオデータのバックアップ
- 編集用ファイルの取得（ダウンロード → 編集 → アップロード）

**注意:**
- これは**シナリオマスタデータ**のエクスポートです。
- 利用履歴や評価データを含む**シナリオ利用ログ**のエクスポートについては、『ログ設計書』を参照してください。

## 6. 運用上の注意点

### 6.1. FAQ削除時の確認事項

FAQを削除する際は、以下を確認してください：

#### (1) 他のFAQからのリンク

削除対象のFAQが他のFAQから参照されている場合、リンクが無効になります。
管理画面で削除を実行すると、参照元のFAQリストが表示されます。
必要に応じて、参照元のFAQ回答文を修正してください。

**システム動作:**
```typescript
async function deleteFaq(faqId: string): Promise<DeleteResult> {
  // 1. このFAQを参照している他のFAQを検索
  const referringFaqs = await searchReferringFaqs(faqId);
  
  if (referringFaqs.length > 0) {
    // 警告を返す
    return {
      status: "warning",
      message: `このFAQは${referringFaqs.length}件の他のFAQから参照されています`,
      referringFaqs: referringFaqs.map(f => ({
        faqId: f.faqId,
        faqPath: f.path,
        categoryName: f.categoryName
      })),
      confirmRequired: true  // 確認が必要
    };
  }
  
  // 2. 参照がなければ物理削除実行
  return await executeFaqPhysicalDeletion(faqId);
}

// 参照しているFAQを検索
async function searchReferringFaqs(targetFaqId: string): Promise<FAQ[]> {
  const allScenarios = await getAllScenarios();
  const referringFaqs: FAQ[] = [];
  
  for (const scenario of allScenarios) {
    for (const faq of scenario.faqs) {
      if (faq.linkedFaqIds.includes(targetFaqId)) {
        referringFaqs.push(faq);
      }
    }
  }
  
  return referringFaqs;
}
```

**管理画面での表示例:**
```
警告

このFAQを削除すると、以下のFAQからのリンクが無効になります：

1. [店頭業務 > スマイル] /科目別に探す/保証/保証人の免除について知りたい/...
2. [融資関連 > 法人融資] /手続き別/担保設定/保証人変更/...
3. [店頭業務 > 相続] /相続手続き/保証人変更/...

本当に削除しますか？
[キャンセル] [削除を実行]
```

#### (2) 過去の問い合わせログへの影響

削除されたFAQから発生した過去の問い合わせログは、`sourceFaqId`と`sourceFaqAnswer`により追跡可能です。
ただし、削除後に該当FAQの詳細情報（階層パス、カテゴリなど）を確認したい場合は、
削除前にシナリオExcelファイルをSharePointからダウンロードしてバックアップしてください。

**復元の可能性:**
- **7日以内**: Cosmos DBのポイントインタイムリストアで復元可能
- **8日以上経過**: SharePointのExcelバージョン履歴から手動復旧が必要

#### (3) 利用統計データへの影響

削除されたFAQの利用統計データ（閲覧数、評価など）は、シナリオ利用ログとして保持されます。
過去の統計分析は引き続き可能です（ログには回答内容も保存されています）。

### 6.2. FAQ階層パス（path）変更時の注意

FAQ階層パスを変更すると、**新しいFAQ IDが生成され、別のFAQとして扱われます。**

#### 影響範囲
- 過去の利用統計（閲覧数、評価数）は新しいFAQ IDには引き継がれません
- 他のFAQからのジャンプリンクは、パス変更後も自動的に追従します（パスベースでリンク解決されるため）

#### 推奨される運用

**軽微な誤字修正の場合:**
- 回答内容のみを変更し、階層パスは変更しない
- 例: 「保証人の免除につ いて」→「保証人の免除について」
  - ❌ pathを変更 → 新FAQ扱い、統計データが分断
  - ✅ answerのみ変更 → 同FAQ扱い、統計データが継続

**階層構造の変更の場合:**
- 新しいFAQとして作成し、古いFAQは削除する
- 例: `/科目別に探す/保証/...` → `/手続き別/保証手続き/...`
  - 意図的な構造変更なので、新FAQ扱いが適切

**具体例:**

```typescript
// ケース1: 誤字修正（pathは変更しない）
// 変更前
{
  faqId: "FAQ-BIZ-A1B2C3-7f8a9c2d",
  path: "/科目別に探す/保証/保証人の免除について知りたい",
  answer: "基本的には保証免除依頼書は必要です。"
}

// 変更後（推奨）
{
  faqId: "FAQ-BIZ-A1B2C3-7f8a9c2d",  // IDは不変
  path: "/科目別に探す/保証/保証人の免除について知りたい",  // pathも不変
  answer: "基本的には保証免除依頼書は必要です。ただし、例外規定があります。"  // answerのみ変更
}

// ケース2: 階層変更（新FAQとして作成）
// 旧FAQ（物理削除）
{
  faqId: "FAQ-BIZ-A1B2C3-7f8a9c2d",
  path: "/科目別に探す/保証/保証人の免除について知りたい",
  // ... 削除される
}

// 新FAQ
{
  faqId: "FAQ-BIZ-A1B2C3-9k1m2n3o",  // 新しいID
  path: "/手続き別/保証手続き/保証人免除",  // 新しいpath
  answer: "基本的には保証免除依頼書は必要です。ただし、例外規定があります。"
}
```

### 6.3. 利用者へのリンク表示

利用者がFAQを閲覧する際、システムは自動的にリンク先の有効性を確認します：

**処理ロジック:**
```typescript
async function renderFaqAnswer(faq: FAQ): Promise<string> {
  let answer = faq.answer;
  
  // 内部リンクを処理
  const linkPattern = /\[([^\]]+)\]\((\/[^)]+)\)/g;
  const matches = [...answer.matchAll(linkPattern)];
  
  for (const match of matches) {
    const linkText = match[1];  // 表示テキスト
    const linkPath = match[2];  // FAQ階層パス
    
    // リンク先のFAQを検索
    const targetFaq = await findFaqByPath(linkPath);
    
    if (!targetFaq) {  // 物理削除済み
      // リンク切れの場合、警告表示に置換
      answer = answer.replace(
        match[0],
        `~~${linkText}~~（このFAQは削除されました）`
      );
    } else {
      // リンク先が有効な場合、クリッカブルに
      answer = answer.replace(
        match[0],
        `[${linkText}](action:jump:${targetFaq.faqId})`
      );
    }
  }
  
  return answer;
}
```

**利用者への表示:**

**リンク有効な場合:**
```
基本的には保証免除依頼書は必要です。

詳細は以下を参照してください：
相続手続きの詳細 ← クリック可能
```

**リンク切れの場合:**
```
基本的には保証免除依頼書は必要です。

詳細は以下を参照してください：
~~相続手続きの詳細~~（このFAQは削除されました）
```

管理者が気づかずにリンク切れを放置しても、利用者には適切なメッセージが表示されます。
ただし、ユーザビリティ向上のため、定期レポートに基づき速やかにリンクを修正してください。

### 6.4. データのバックアップと復元

#### Cosmos DB（シナリオの最新版）

**バックアップ:**
- 継続的バックアップモード: 2分ごとに自動バックアップ
- 保持期間: **7日間**

**復元手順:**
```
誤ってFAQを削除した場合（7日以内）:
1. Azure Portalにログイン
2. Cosmos DBアカウント → 「データエクスプローラー」
3. 「復元」ボタンをクリック
4. 復元したい時点（削除前の日時）を指定
5. 復元を実行
6. 復元されたデータを確認し、現在のデータベースに反映
```

**注意:**
- 8日以上経過すると復元不可能
- この場合、SharePointのExcelバージョン履歴から手動で復旧する必要がある

#### SharePoint Online（原本Excel）

**バージョン履歴:**
- AvePointにより6時間ごとにバックアップ
- 保持期間: **5年間**

**復元手順:**
```
Cosmos DBから削除されたFAQを復旧する場合（8日以上経過）:
1. SharePoint Onlineの該当サイトにアクセス
2. シナリオExcelファイルを開く
3. 「バージョン履歴」を表示
4. 目的の日時のバージョンを選択
5. ダウンロード
6. 管理用ボットから再度アップロード
```
